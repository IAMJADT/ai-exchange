# AI 开发全流程管控手册

版本：v1.5　状态：活文档　维护：晓备\_AI-001（IMA Copilot）

适用：从需求到运维、全部由 AI 执行的项目（网站、小程序、内部系统、脚本工具均适用）。推行方式＝迭代交付：前半程原型驱动迭代（形态未定，靶子是原型），后半程基线驱动迭代（形态已定、改的是内部，靶子是指标）。每轮出能看的东西、每轮验收、基线冻结后才进开发。

## 〇、这份手册解决什么

一句话：让 AI 从需求到运维全程干活，而你不失控。

三条铁律，全篇都从这三条长出来：

1. **用交付物当闸门，不用进度当闸门。** AI 说"做完了"不作数，交出规定的那份东西、且被判据判过，才准进下一段。
2. **机器判对错，人只判"要不要"。** "通过 / 不通过"一律由可执行的判据产生，AI 自述与文字报告一律不作证据。
3. **AI 没有三样东西**：正式环境的写权、物理删除的权、自行修复生产环境的权。

### 〇·1 判据分级（v1.4 新增，全手册的地基）

铁律 2 说"机器判对错"，但没说清什么样的东西算"判据"。补一张表，凡判定"通过"必须先说出它属于哪一级：

| **级别**  | **判据形态**                            | **谁有否决权**         | **举例**                   |
| ------- | ----------------------------------- | ----------------- | ------------------------ |
| **A 级** | 机器产出：测试结果、构建输出、静态检查、全量 diff、门禁脚本退出码 | **机器，唯一有效**       | 测试跑过、diff 里只有声明过的文件、真机截图 |
| **B 级** | 脚本可查：编号对应、清单完整、文件存在、字段齐全            | **脚本**            | RT 编号能倒查到用例与上线记录         |
| **C 级** | 没有独立判据：好不好用、顺不顺手、命名顺不顺眼             | **只有决策人亲自用一遍才能判** | "这个按钮点起来别扭"              |

四条判据规则，缺一条整套体系就回到"AI 自证"：

1. 任何"通过"必须有 A 级或 B 级证据；**只有 C 级意见，视为不通过**。
2. 执行方可以提 C 级建议，但**无权判 C 级通过**——C 级只能由决策人自己说了算。
3. 决策人的判断**只在 C 级有效**，不得用它推翻 A 级。机器说构建失败，不能因为"我觉得没事"放过。
4. C 级不是"风险由决策人承担"，而是"**C 级必须由决策人亲自验一次**"。看不懂代码不影响做 C 级判断——点一遍就知道顺不顺。

### 〇·2 术语：三个名字各管哪一段

| **名字** | **管哪一段**                    | **靶子是什么** | **什么时候用**      |
| ------ | --------------------------- | --------- | -------------- |
| 迭代交付   | 全流程总称                       | ——        | 一直             |
| 原型驱动迭代 | 形态还没定：S0 立项、S1 三件套、上线后的界面改版 | 原型        | 说不清要什么的时候      |
| 基线驱动迭代 | 形态已定、改的是内部：性能调优、架构改造、并发与稳定性 | 指标基线      | 上线后优化、demo 转正式 |

这三个不是三种方法论，是同一套流程换靶子。靶子换了，闸门位置不变。

配套说明：本手册属于敏捷家族的一种裁剪版，但不等于敏捷。敏捷的价值观里有相当一部分是管人的（自组织团队、面对面沟通、可持续节奏），对 AI 执行不适用；我们只要它的骨架——短迭代、每轮出能用的东西、客户随时参与，配上瀑布的严谨——每段有闸门、基线冻结、证据留痕。所以名字叫「迭代交付」，不叫「敏捷交付」，避免被人拿敏捷标准来套。

## 一、四个角色（各自只做一件事）

| **角色**                              | **只做一件事**                                           | **不做**                   |
| ----------------------------------- | --------------------------------------------------- | ------------------------ |
| 你（决策人）                              | 定需求、判 C 级（体验好不好）、签选型的代价、按上线按钮、紧急授权                  | 不看代码、不做技术判断              |
| 晓备（管控层）                             | **定义 A/B 级判据、维护门禁脚本、自己去取证据、把机器结果翻译成人话**、守禁区、留痕、维护索引 | 不做产出（不代替执行方写代码/做设计）      |
| 执行 AI（WorkBuddy / 豆包 / CodeBuddy 等） | 做原型、写代码、跑测试、出证据包                                    | 不自判合格、不碰正式环境、不删数据、不改门禁脚本 |
| 机器（流水线 / 门禁脚本 / 监控）                 | 自动判据、自动告警、自动留记录                                     | 不做价值判断                   |

**最容易被忽略的一条：执行 AI 不能给自己发合格证。谁做的谁不能判过。**

### 一·1 晓备的否决权从哪来（v1.4 新增，回应外部意见）

晓备也是 AI，如果它只是"读另一个 AI 写的报告然后点头"，那独立性就是名义上的。所以它的权力必须来自机制，不来自角色名：

1. **复跑权**：它有权在任何时候用同一个脚本重跑一遍，机器结论不一致以复跑为准。
2. **自取证据权**：复核不看执行方写的报告，自己拉全量 diff、跑命令、看原始输出、抽样复现。
3. **门禁脚本维护权**：脚本由它写、它改，执行方只读（见 S3）。
4. **翻译职责**：把 A/B 级结果翻成决策人能懂的一句话结论，**不产生新的判据**。

它不能做的事：不能凭"我觉得"否掉 A 级结果，不能替决策人判 C 级。

## 二、全流程七段（总览）

| **段** | **阶段**    | **执行**     | **交出什么**                 | **谁来判**        |
| ----- | --------- | ---------- | ------------------------ | -------------- |
| S0    | 需求立项      | 你 → 晓备整理   | 三句话立项（问题 / 谁用 / 大概做什么）   | 你（闸）           |
| S1    | 原型与流程设计   | 执行 AI      | 三件套：原型 + 状态流程表 + 权限表     | 晓备查 B 级、你看 C 级 |
| S1B   | 非界面迭代（按需） | 执行 AI      | 指标基线表 + 压测方案 + 回退方案      | 机器出数 + 晓备复核    |
| S2    | 技术方案      | 执行 AI      | 七项（见下）+ **两案一荐表**        | 晓备审、你签代价       |
| S3    | 开发        | 执行 AI      | 代码 + 全量改动 + 自测证据包        | A 级机器门禁 + 晓备复跑 |
| S4    | 测试        | 执行 AI + 机器 | 用例（含独立来源）+ 真机回归报告 + 缺陷台账 | 机器，晓备看结论       |
| S5    | 上线        | 你按按钮       | 上线单、回退点、备份恢复演练记录、上线记录    | 你（闸）           |
| S6    | 运维        | 执行 AI      | 巡检报告、告警、工单（或 Lite 三件事）   | 晓备复核、你收日报      |

**人工闸只有三道**：S0 立项确认、S1 三件套验收、S5 上线按钮。其余机器判、晓备复核。这就是"全 AI 但不失控"的结构。

## 三、逐段细则

### S0 需求立项（十分钟，不写长文档）

输入：你的一段话——想到哪说到哪，不必整理。

开工前只要求三样，十分钟能出：

| **开工三样** | **要求**          | **反例** |
| -------- | --------------- | ------ |
| 要解决什么问题  | 一句话说清痛点         | 做个系统   |
| 谁用、什么场景  | 具体到人和动作         | 给用户用   |
| 这期大概做什么  | 粗线条，允许不完整、允许后面补 | 空着     |

闸门规则：「验收标准」和「本期不做」不再是开工前置——它们在 S1 对着原型逐步长出来。开工前唯一的要求是上面那三句话，缺任何一样都不开工。

为什么这样改：需求从来不是一次能想全的，人在看到原型之前根本说不清要什么。硬要求开工前写全验收标准，只会催生一份编出来应付的文档，最后照样返工。真正要锁住的不是"想得全"，是"改得留痕、有冻结线"。

你的动作：十分钟说清三样，然后直接看原型。想到新需求随时说，但只进「需求记录」（RT 编号），不许当场改本期。

### S1 原型与流程设计（三件套）

产出＝三件套，同一轮出、同一套编号、同一次验收：① 可点原型　② 业务状态流程表　③ 角色权限表；另附 UI 规范与冻结版本号。三件套按页面裁剪——纯展示页只出原型，会流转的业务页才出②③。若本次迭代不含界面变更（性能、架构），不走这段，走 S1B。

三件套各管什么：

① **原型**：每页带批注——这页干什么、有哪些字段、点了会发生什么。页面跳转不单独画箭头图：能点的原型本身就是跳转说明，点得通就对、点不通就是错；只有「点按钮不跳页」的动作（弹窗、改状态、发通知、扣额度）必须在批注里写明。

② **业务状态流程表**：每行＝当前状态 / 谁能操作 / 做什么 / 变成什么状态 / 失败或异常怎么办。原型只能证明「有这个页面」，证明不了「业务跑得通」；这张表才是 AI 写代码与验收的唯一依据。

③ **角色权限表**：谁能看到什么、能点什么。按角色列成表，不画成流程图。

**硬规矩（v1.4 补充）**：

* 原型期不接后端、不连真实数据、不写部署脚本；
* 定稿时打版本号（如 v1.0-frozen），之后要改＝出新版本并重新确认；
* 实现阶段偏离原型＝缺陷，不是"优化"；
* **原型附「保真度声明」**：逐页标明哪些是示意（配色/间距/装饰可以不同）、哪些是最终交互（不得偏离）。免得上线后扯"和原型不一样"。
* **每页必须有六种状态稿**：空态、错误态、超长文本、无权限、加载中、重复提交。（v1.3 只要求前三种，后三种是漏测重灾区。）

按页面裁剪，不许一刀切：纯展示页（首页、介绍页、图集、说明页）只出原型，不做②③；只有「会流转的业务页」才出状态表与权限表。判断标准一句话：这页上的操作能不能改变某个东西的状态——不能，就不做表。

**轮次上限（v1.4 新增）**：S1 最多 3 轮定稿，超出须你显式说"再来一轮"。这是防止"再改改"把项目无限拖住的唯一闸。

判据（机器/晓备可查）：

1. 每个页面能点通，无死链、无空白页
2. 每种页面都有六种状态稿
3. 状态流程表里每个状态，都能在原型上找到对应的界面与按钮
4. 权限表里每个角色，都能在原型上走通一条完整路径
5. 图与表编号一一对应（原型上标的编号，状态表里必须有同一行）
6. 页面上的文字、编号、数量，与 S0 的三句话对得上
7. 每页有保真度声明

失控点：只出原型不出流程表——页面都长得对，业务却跑不通（状态漏了、驳回没人做、失败没兜底）。原型能证明"有这个页面"，证明不了"业务走得通"。

你的动作：看三件套，重点看「一条真实业务能不能从头走完」；一次说一个问题，我记成 RT 编号条目。分 2\~3 轮：第一轮看骨架、第二轮看字段与流程、第三轮定稿；定稿即冻结基线，之后的新想法进「下期清单」，不回头改本期。

### S2 技术方案

这是最容易被跳过、也最该补的一段。 AI 写代码太快，没有方案就一头扎进去，三个月后改不动。

产出（七项，缺一不可）：

| **项**              | **要能回答的问题**                      |
| ------------------ | -------------------------------- |
| 技术选型               | 用什么、为什么、被否掉的方案是什么                |
| 数据模型               | 有哪些表/对象、关系怎么连                    |
| 接口清单               | 前后端怎么对话、谁调谁                      |
| 部署拓扑               | 跑在哪、几个环境、怎么发布                    |
| 数据存续               | 哪些能删、删了是软删还是硬删、留痕落在哪             |
| 回退方案               | 出事怎么退回去、多久能退                     |
| **安全与合规**（v1.4 新增） | 谁能访问什么、传输与落库是否加密、有没有审计日志、收不收个人信息 |

关于"性能与容量"（P95、QPS、峰值、存储年增长）：**小项目不放进 S2**。原因的分别对待——安全合规后期补不回来（数据已经收进来了），性能可以放到 S1B 用基线驱动补（改之前先量、改完再量）。凡涉及收个人信息或对外开放注册的项目，安全合规一栏不许留空。

**技术选型＝两案一荐（v1.4 改，修掉 v1.3 的自相矛盾）**

v1.3 一边说"决策人不做技术判断"，一边说"选型必须你确认"——这两句是矛盾的，结果只能是盲签。改成固定格式：

| **项** | **方案 A** | **方案 B** |
| ----- | -------- | -------- |
| 一句话说明 | ​        | ​        |
| 首年成本  | ​        | ​        |
| 维护难度  | ​        | ​        |
| 迁移成本  | ​        | ​        |
| 主要风险  | ​        | ​        |

表下方一行：**推荐 X，理由是 \_\_\_\_\_\_**。

你只回答「接受推荐」或「选另一案」。**你签的是代价，不是技术。**

闸门规则：

1. 技术选型必须你确认（你不能被默认代替拍板）；
2. 数据存续规则没定，不许开工；
3. 涉及个人信息或对外开放注册的，安全合规项没填，不许开工。

失控点：跳过 S2 直接写代码。后果是数据删了找不回、出了事退不回去、个人信息裸奔——这三样都是不可逆伤害。

### S3 开发

产出：代码 + 全量改动清单 + 自测证据包。

三道闸：

1. **提交关**：执行 AI 只能推 dev 分支，主分支受保护，推不进去。
2. **机器关**：门禁脚本全绿（构建、测试、文档同步、禁区文件）。
3. **复核关**：晓备**自取证据**（拉全量 diff、自己跑命令、看原始输出），对照禁区清单 + "说的和做的是否一致"，出大白话报告。

**门禁脚本归属（v1.4 新增，这条是命门）**

* 门禁脚本由管控层（晓备）维护，执行方**只读**；
* 脚本任何变更都要留 diff 并经决策人之外的独立方（晓备）确认；
* 执行方提交里若包含脚本目录的改动，一律视为越界打回。

理由很直白：执行方如果能改判据，就能写一个永远绿的脚本，整套门禁立刻变成装饰。

判据：详见《代码风险管控体系（通用模板）》五道关（本手册不重复，那份是 S3\~S5 的细则）。

最要紧的一条：复核必须看全量改动，不能只看"我关心的那几个文件"。历史上就出过——只筛了自己改的 CSS，夹带了一个禁区文件一起合并进去。

失控点：谎报（说改了两行，实际改了五个文件）、夹带（顺手改禁区）、顺手重构。

**禁区与技术机制（v1.4 新增）**

铁律 3 说的三样禁区，只写在文档里是没有强制力的——"规定不许"不等于"做不到"。每条禁区必须绑一个技术机制；写不出机制的，标注「仅约定，风险已知」，不许当控制手段宣传。

| **禁区** | **强制机制**                           |
| ------ | ---------------------------------- |
| 正式环境写权 | 执行方用独立只读凭证；部署由人触发，AI 无部署密钥         |
| 物理删除   | 数据库账号无 DROP / TRUNCATE 权限；业务删除一律软删 |
| 自行修生产  | 生产环境无 SSH 权限；热修必须走审批单 + 事后补记录      |
| 改主分支   | 分支保护，执行方只能推 dev                    |
| 改门禁脚本  | 脚本目录对执行方只读；含脚本改动即打回                |

### S4 测试

产出：测试用例 + 真机回归报告 + 缺陷台账。

**用例必须有两个来源（v1.4 改）**

v1.3 只要求"从 S1 三件套逐条反推"，这是循环论证：状态表漏了一个状态，测试就永远测不出来，因为只测表里有的东西。所以：

1. **来源一（同源）**：状态流程表每一行、需求记录每一条 RT，至少一条用例。
2. **来源二（独立，至少占三分之一）**：
   * 决策人真实走查（当普通用户乱点，不按说明书走）
   * 线上监控与真实报错
   * **异常注入清单**（固定附件，每条需求至少命中一项）：断网、重复提交、并发、越权、超长、空值、时区、金额精度。

不硬钉"30%"这种数字——数字会催生凑数。钉的是「每条需求至少配一条异常注入用例」。

硬规矩：

1. 用例从 S1 三件套 + 独立来源，两路都要有；AI 自己想的用例不算数。
2. AI 不得自判"通过"。通过必须有：截图、命令输出、日志。没有证据＝未通过。
3. 修一个缺陷，必须全量回归，不能只测修的那处。

判据：状态流程表 / 需求条目 ↔ 用例 ↔ 结果，三者可一一对应；有缺口＝不通过。

失控点：AI 专挑自己写得顺的路径测，边界情况（空数据、超长、并发、断网）全部漏掉；以及需求本身漏了状态，测试跟着一起漏。

你的动作：不用管过程，看结论——哪几条不通过、影响什么。

### S5 上线

产出：上线单（版本号、改动范围、回退点、影响面、是否需停机）。

固定动作，顺序不能变：

1. 打快照（回退点）
2. 上线
3. 10 分钟内健康检查（首页、关键页、关键功能，各点一遍）
4. 留上线记录

**备份必须真恢复过（v1.4 新增）**

代码能回退 ≠ 数据能回来。加两条：

1. 凡涉及数据结构或业务逻辑调整，必须单独写「数据回退方案」，不能拿"代码回滚"顶。
2. 备份每季度**实际恢复一次**并记录耗时。**没恢复验证过的备份，视为不存在。**

理由：备份是整套体系里最容易被当成"已经有了"的假安全。文件在、定时任务绿、日志正常，都不等于能恢复。

**灰度 / 分批发布（v1.4 新增）**：小项目可跳过，但必须知道有这个选项。上线单里加一栏"是否灰度：是 / 否，理由"。

闸门规则：上线按钮你按。执行 AI 对正式环境只有读权。

失控点：AI 顺手替你发了；没打回退点就上线；备份从没验过却当成能救命。

### S6 运维

产出：监控告警配置 + 每日巡检报告 + 故障工单。

权限边界（这条最容易被"好心"突破）：

* AI 有的权：发现、报告、给建议
* AI 没有的权：直接处置生产环境
* 修复必须回到 S3→S5 走一遍；紧急热修必须当次你授权，且事后补记录

**Lite 运维模式（v1.4 新增，给单人 / 小项目）**

流程不能压垮唯一的负责人。单人项目只保留三件事：

1. 每日自动健康检查（脚本跑关键页，失败就告警）
2. 错误告警直达负责人
3. 故障记录（出过什么事、怎么好的，一行一条）

日巡检报告、工单系统、SLA 统计可以省。**降级不等于免责**：告警必须真的有人收、真恢复演练照做。

判据：任何生产变更都有工单号；巡检报告每天按时出；告警有响应记录。

失控点：AI 为了"赶紧修好"，直接上生产改，把小事搞成大事。

### S1B 非界面类迭代（形态已定，改的是内部）

> v1.3 原称 S1′，v1.4 改为 S1B——撇号在检索、文件名、跨系统引用中经常丢失，实测踩过。

什么时候走这一段：本次迭代不含界面变更——性能调优、架构改造、并发与稳定性、数据迁移。这时 S1 的三件套不适用（原型没变，看不出任何东西），换成另外三样：

1. **指标基线表**：现在是多少 → 目标是多少 → 怎么测。指标必须具体：P95 响应时间、QPS、错误率、内存峰值。没有基线数字，不许开工——否则改完谁也说不清好没好。
2. **压测 / 验证方案**：怎么造压力、压多久、看哪几个指标、什么数值算通过。不许用「我试了一下感觉快了」当结论。
3. **回退方案（比界面类严得多）**：界面改坏了一键退回就行；架构改坏了，数据可能已经按新逻辑写入，退回去这些数据怎么办必须提前写清。这一条写不出来，就不许动架构。

闸门照旧：基线不清不开工；验收必须拿数据说话，机器出数、晓备复核、你只看结论；上线走 S5 同一套（快照 → 上线 → 健康检查），只是健康检查项换成指标前后对比；上线后 24 小时观察期，期内出事按回退方案执行，不许现场临时想办法。

## 四、止损与退出条件（v1.4 新增）

没有 kill criteria，项目不会停下来，只会拖着烂。

触发条件（任一命中即暂停，不再往下推）：

1. 同一功能连续 2 轮验收不通过
2. 成本超出预算 2 倍（预算在 S2 定，见下）
3. 核心第三方依赖失效且无备选（如某个服务停服、封号）
4. **决策人连续 4 周未参与**——注意：这条不判死刑，触发的是**降档**（见下）

决策人长期不参与的处置（v1.4 按实际情况修正）：你同时管多个品牌，4 周不碰某个小项目是常态，不该因此判项目死刑。正确动作是二选一：

* 降到 Lite 档（S1 只出原型不出两表、S6 只留三件事），继续轻推；
* 或标为「挂起」，从预算与排期里摘出去，等你回来说继续。

触发后的动作：冻结 → 归档现状 → 三选一（继续 / 重做 / 放弃）→ 留记录。**不许无声无息地烂在那里。**

配套：**预算与轮次**（在 S2 定）

* S1 原型最多 3 轮定稿（超出须你显式续期）
* 单个功能设费用 / 用量上限
* 每轮记录消耗，累计超预算 1.5 倍触发复核

理由：AI 迭代没有天然终点，"再改改"可以无限循环，而每次循环都真花钱。

## 五、Lite 档与适用范围（v1.4 新增）

流程要适配项目，不能反过来。先判档，再决定走几段。

| **档**    | **适用**                        | **走哪几段**                        | **省掉什么**                                |
| -------- | ----------------------------- | ------------------------------- | --------------------------------------- |
| **Lite** | 一次性脚本、单一展示页、三天内能完的小工具、试验性点子   | S0 三句话 → 直接做 → 你点一遍 → 上线        | 三件套只出原型、不做状态表、不做权限表、不做 S2 全案、不做 S4 用例台账 |
| **标准**   | 官网改版、内部系统、会给别人用的工具            | S0 → S1 三件套 → S2 → S3 → S4 → S5 | 无（默认档）                                  |
| **全档**   | 涉及收付款、账号权限、个人信息、不可逆删除、多 AI 协作 | 全部七段 + 全部闸 + 备份演练 + 凭证交接        | 不许省                                     |

两条不许在 Lite 档省：

1. **上线前打快照**（回退点）
2. **你按上线按钮**

不适用本手册的场景：一次性数据导出、纯文档整理、只读查询脚本——这类不要走流程，直接做。

## 六、贯穿全程的六条线

1. **编号贯穿**：RT-0001（需求）之下挂任务 TASK（一对多，写作 RT-0001-a / -b，不另起一套编号）——需求 → 任务 → 提交 → 用例 → 上线记录 → 运维工单，一条线串到底。任何时候能倒查"这东西谁做的、为什么做、什么时候上的"。
2. **三环境分离**：dev（开发）→ preview（预览）→ prod（正式）。执行 AI 只能写前两个。
3. **文档同步门禁**：代码改了文档没改＝门禁 FAIL。这是防"三个月后文档全废"的唯一办法，靠自觉一定失败。**（v1.4 明确驳回"降为告警"的建议，理由见变更日志；解法是缩小强判定范围——只对本次改动涉及的文档章节做强判定，不做全库比对。）**
4. **单一真值源**：每个项目一份项目状态文档 + 一份决策记录。AI 只读，不另存副本。发现两份口径，当场收敛成一份。
5. **随时可回退**：改动前必打点，回退命令必须真的测过一次（没测过的回退＝没有回退）。
6. **凭证可交接（v1.4 新增）**：代码仓库、域名、云账号、数据库、第三方服务、支付通道、监控、备份存储——每项记「归属人 / 权限级别 / 交接方式 / 轮换周期」。密钥只存在密码管理器，**不写进任何文档**。清单本体见《账号与钥匙分类表》，本手册不重复。理由：换 AI 的卡点从来不是代码，是凭证在谁手里。

## 八、三个高频失效点（实话）

1. **文档漂移**：AI 最不爱改文档。这是全 AI 开发的头号后遗症，必须做成硬门禁，不能靠提醒。
2. **多 AI 无主**：几个 AI 各推各的，最后没人对整体负责。所以必须有一个固定管控角色（晓备），不做产出，只把关。
3. **"顺手优化"**：AI 常顺手重构、顺手美化。看着是好事，实际是范围与风险双失控。凡超出任务卡的改动，一律打回。

## 十、诚实说明（边界）

这套体系不是"绝对不出事"，是"错一步不会死"：任何改动都能退，任何上线都有记录，任何 AI 都不能独自把系统搞坏。

项目类型决定放权程度：内部工具、官网、脚本类可以全程放给 AI；涉及收付款、账号权限、不可逆删除的，必须保留人工代码审计这一层。

手册写得再好，也要有一个真项目跑通第一遍才站得住。第一次跑，允许流程粗糙，但闸门位置不能少。

**v1.4 自查到的自身弱点（写在这里，不藏）**：这套体系十八个条款里，十七条在"防 AI 失控"，只有两条在"防流程过重"。对一人管多品牌的实际情况，更常见的失败不是系统被搞坏，而是流程太重、项目推不动、最后被绕过。所以第五章的 Lite 档不是补充，是必须项。

## 十一、v1.5 修订（2026-11-21）

**1. 截图降为 B 级判据，并加证据三要素。** 〇·1 原把「真机截图」列进 A 级，与本文自己写的「截图可能来自本地机、可能是三天前的」互相矛盾，现修正：A 级只保留命令输出、CI 日志（带 commit hash）、产物 hash、门禁退出码；截图归 B 级，且必须同时具备环境标识（dev / preview / prod）、commit hash、采集时间，缺一即判「未验证」。管控方须能在 5 分钟内用同一命令独立复现，复现不出的证据不算数。

**2. S3 新增红队注入。** 每季度随机抽 4 条，故意注入本应被拦的改动（改禁区文件、删测试、伪造通过态），记录注入内容、执行命令、退出码、门禁实际反应、时间戳。**不红即缺口，不许解释**——「这次刚好不算」「这条不适用」一律不接受，记为已知缺口写进下一版。弹药清单由复核方出，不由门禁维护者出；且必须盲抽，公开全测等于给对方一份补丁说明书。

**3. 六·3 文档同步门禁加映射定义。** 只校验本次 diff 的代码路径是否命中 docs/ 下已登记的映射条目，且文档 diff 必须含对应 RT 编号，否则 FAIL。防「改一个空格冒充文档已同步」。范围缩小到能实现，强度保持不变。

**4. 第四章补项目规模触发条件。** 单项目需求数 > 60 且任务拆分率 > 30%，或同时并行 ≥ 3 个执行 AI 时，需求号与任务号改双轨（RT / TASK）分离；未达此规模，用 RT-0001-a 从属编号。排期表按「RT 号 + 数值序号」双键排序，不按字符串排（-a / -z / -aa 会乱）。

**5. S5 预授权回滚三边界。** 允许 AI 在无人值守时自动回滚，但限三条：① 唯一动作是执行**已演练过的**回滚脚本，不修 bug、不改配置、不重启改造；② 回滚脚本本身须 hash 固定，执行前校验未被改动，未演练过的不许预授权；③ 回滚后**自动僵持**，系统停在上一版等 RL 决定「修」还是「保持」，AI 不许接着往前推。僵持期每小时提醒一次，直到 RL 响应，不许静默停摆。

**6. S2 合规五项（全档项目必填）。** 最小必要收集 / 留存期限 / 删除请求响应 / 第三方共享清单 / 数据出境。留空不许开工。理由：安全合规后期补不回来（数据已经收进来了），性能可以放 S1B 用基线驱动补。

**7. 交接问法改写。** G4 原问法「做到哪 / 为什么这么设计 / 什么不能碰」考的是记忆，能背文档就能过。改为：**「如果我现在让你改 X，你会先动哪个文件、为什么不是另一个？」** 答成「我会先读 README」「我会先看看代码」＝**未通过**；必须说出具体文件路径和排除理由。凭证交接解决钥匙，这道题解决理解。
