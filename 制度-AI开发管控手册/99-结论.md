# 99 · 结论

## 结论（2026-11-21）

### 1. 定了

1. **手册 v1.4 已发布**（2026-11-20 23:23），12 处实质修订、2 条驳回（均写明理由）。
2. **7 条修订待落 v1.5**：截图降 B 级并加证据三要素 / S3 新增红队注入（弹药由 TRAE 出）/ 文档同步门禁加映射定义 / 项目规模触发条件（60 条·30%·3 AI）/ S5 预授权回滚三边界 / S2 合规五项 / 交接问法改写。
3. **AI 间往来改用云效 Git 仓库**，一个总仓库 `ai-exchange`，按话题分目录，不按 AI 分、不塞进项目代码仓库。
4. **记录规矩三条**：只能追加不能修改 / 以专属账号加 SSH 密钥提交（文件名署名不算）/ 引用必须原文。
5. **一个 AI 一个子账号**，包括晓备自己；密钥用 SSH 不用访问令牌（令牌会过期且静默失效）。
6. **红队测试**：弹药清单由 TRAE 出，晓备执行并公开原始结果；每季度盲抽 4 条，不预告抽哪 4 条。

### 2. 没定

1. **v1.5 什么时候落** —— 等 RL 拍板。手册归 RL，晓备不因对方一句"可以投入使用"就自己改。
2. **子账号什么时候建** —— 需 RL 在阿里云控制台操作（RAM 子用户 + 云效授权 + 贴 SSH 公钥）。
3. **红队第一次执行时间** —— 定在 v1.5 落地后一周内，靶场用选址客的门禁流水线（不碰生产发布）。
4. **企业实名变更** —— RL 另行推进，与本仓库解耦。

### 3. 被否的方案（记下来，免得以后重新提）

| 方案 | 为什么不采用 |
|---|---|
| 腾讯文档承载往来记录 | TRAE 打不开 |
| 服务器静态网页承载 | 只有晓备能写，必成"抄写员" |
| 各 AI 各建一个仓库 | 仓库数随 AI 数增长，半年后找不到 |
| 放进项目代码仓库 | 权限错配、随代码归档消失、交接混乱 |
| 两个人共用一个账号 | 服务器记录的提交人相同，追不了责 |
| 使用访问令牌 | 会过期且静默失效，已吃过一次亏 |
| 目录控制读写权限 | 目录不是权限边界；同一令牌是仓库级权限 |

### 4. 未解决的分歧（长期挂档）

**门禁脚本逻辑本身写错的风险，红队注入测不出来。**
红队是黑盒测（打进去看红不红），"脚本自己写错了"是白盒问题。写脚本的人测脚本，闭环不了。
**唯一真解是外部真人开发者做一次代码审计（几小时、要花钱）。** 在有第三个主体之前，这条不假装解决。
