# 2026-11-21 · Token 类型与账号归属

## 结论

**先查仓库归属是「个人账号」还是「组织」。个人账号名下的仓库，Token 一律用 classic + `repo` scope，不要试 fine-grained。**

## 判据（一条命令，5 秒）

```bash
curl -s https://api.github.com/users/<仓库所有者> | grep '"type"'
```

- `"type": "User"` → 个人账号 → **classic（`repo` scope）**
- `"type": "Organization"` → 组织 → fine-grained 可用（可精确授权到单个仓库）

`IAMJADT` 实测结果是 `"type": "User"`。

## 为什么（这是 GitHub 的硬限制，不是配置问题）

fine-grained token 对**别人个人账号下的仓库**只有读权限。写操作一律返回：

```
403 Resource not accessible by personal access token
```

这是 GitHub 文档写明的限制，调参数、改选项都绕不过去。

## 代价（已经付过的）

2026-11-21，布丁与 RL 为这件事连续白调了三次 token，全部卡在 403。根因是**先选了工具、后查了前提**。

**正确顺序永远是：先确认环境约束，再选实现手段。**

## 规范

1. 每个 AI 用**自己的账号**生成自己的 token，**不共用**。共用会让 `author` 与操作人不一致，署名失效。
2. classic token 勾 `repo` 即可，**不要勾 `admin`、`delete_repo`**。
3. 有效期建议 **90 天**，到期前换新。7 天太短，会让"续期"变成每周一次的人工打断。
4. token **只存环境变量**，不写进任何文档、不进记忆、不进仓库。

## 附：直推 main 的说明（一并记档）

**事实**：2026-11-21 建库初期，共 6 次提交直接推到 main（`a19611c`、`b24e0ef`、`1fb3277`、`536820b`、`53e4a86`、`bc20590`），另有 2 次安装型提交（`af62660`、`96e25da`）。

**原因**：当时分支保护未生效（免费个人账号的私有仓库不执行分支保护）。

**处理**：**不追溯改写历史**。改写历史比留着更坏——第一次就破「不改历史」的规矩，后面就没人守了。

**现状**：仓库已改为公开，分支保护已生效并实测拦截成功（`GH006: Protected branch update failed`）。从 2026-11-21 21:00 起，任何直推 main 都会被 GitHub 拒绝。

**另记**：为绕过付费限制而安装的 `guard-main` Actions 守卫，实测未生效（空提交 `9288d6c` 未被回滚）。原因之一是 `git revert` 对空提交报 `nothing to revert`；也可能是 Actions 写权限未开。**决定：删除该守卫，改用 CI 断言防内容篡改。** 一个坏掉又不报警的守卫，比没有更糟。
